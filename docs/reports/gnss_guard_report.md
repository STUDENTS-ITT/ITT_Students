# Отчёт: защита СНС (GNSS guard) в ITT_Students-VO-FastFreak-homography

## 1. Назначение

Модуль защиты СНС (`nav::SnsGuard`) выполняет предварительную проверку измерений спутниковой навигационной системы перед их использованием в коррекции фильтра Калмана. Цель — исключить применение заведомо некорректных или устаревших СНС-кадров, которые могут привести к скачкам навигационного решения, расходимости оценок и некорректной коррекции ошибок инерциальной системы.

Реализация выполнена с адаптацией под структуру данного проекта (VO/FastFREAK/homography, цикл `main.cpp` + `nav::step`).

## 2. Затронутые файлы

| Файл | Изменение |
|---|---|
| `src/navigation/gps_processor.h` | Добавлены `enum class SnsStatus { VALID, INVALID, STALE }`, `enum class SnsReject { NONE, NONFINITE, RANGE, ZERO_FIX, SPEED, ALTITUDE, TIME, JUMP_POS, JUMP_VEL }`. Сохранён `SnsSample::sig_scale` (используется в проекте, guard его не трогает). |
| `src/ins/ins_filter.h` | Добавлена структура `ins::KalmanConfig` и глобальный объект `ins::kalman_cfg` с параметрами защиты: `gnss_guard_on`, `gnss_vel_plaus`, `gnss_silence_timeout_s`, `gnss_alt_band_m`, `gnss_dt_max_s`, `gnss_jump_pos_m`, `gnss_jump_vel_ms`. |
| `src/navigation/gnss_guard.h` | **Новый файл.** Реализация `nav::SnsGuard` (уровни 1–2): валидация кадра + детект пропадания (STALE). |
| `src/navigation/trajectory.h` | В `nav::step(...)` добавлен параметр `SnsGuard &guard`. Перед коррекцией вызывается `guard.update(...)`. Коррекция Калмана и ввод поправок выполняются только при `sns_ok == true`. |
| `src/main.cpp` | Подключён `gnss_guard.h`. Создан экземпляр `nav::SnsGuard sns_guard`. В основной цикл передаётся `nav::step(..., sns_guard)`. |

## 3. Поток данных и место защиты в алгоритме

### 3.1. Общая схема цикла

1. **Инициализация/выставка** (`main.cpp`): чтение `gps.dat`+`angle.dat` для опорного сканирования, грубая выставка (`get_angle_start`), формирование `NavState`.
2. **Стартовый участок** (первые `START_SAMPLES`, 180 с при 200 Гц ИМУ): интегрирование не выполняется как полноценный навигационный цикл с коррекцией; выполняется привязка по референсу и запись начальных записей. Защита СНС на этом участке **не используется** (вызовов `step` с guard нет) — поведение соответствует исходной логике проекта.
3. **Основной цикл** (`while (imu.next(row))`): для каждого валидного отсчёта ИМУ читается опорный кадр `ref` (`SnsSample`) из `SnsReader` и вызывается `nav::step(i, row, ref, state, log, sns_guard)`.

### 3.2. Что делает `nav::step`

На каждом такте ИМУ:
- Вычисляется `dt` по времени ИМУ (`ins::sampleTime(row)`), обновляется матрица перехода из связанной в навигационную СК `C`.
- Выполняется **прогноз** фильтра Калмана (`ins::predict`) по текущим ускорениям/угловым скоростям и модели ошибок.
- Выполняется **инерциальное счисление**: ускорения в навигационной СК, интегрирование скорости и координат (`integrateVelocity`, `integratePosition`), интегрирование ориентации (`eulerRates`, `ins::integrate`). Обновляется `NavState`.
- Раз в `SNS_DECIMATION` отсчётов (момент коррекции по СНС, ~1 Гц):

```cpp
const bool sns_ok = guard.update(ref, time_s, ins::kalman_cfg);
...
if (sns_ok) {
    // формирование bins из текущего решения ИНС
    // ins::correct(bins, ref.measurement(), st.x, st.P)
    // ввод поправок x в lat/lon/alt/V/att, коррекция ba/bg
    // обнуление x, запись лога
} else {
    // коррекция по СНС НЕ выполняется
    // x обнуляется, запись лога выполняется
}
```

**Критическая точка взаимодействия:** `SnsGuard` располагается **между** чтением/подготовкой `SnsSample` и вызовом `ins::correct`. Только при `VALID` измерение попадает в вектор невязки `z = bins - ref.measurement()` и влияет на матрицы/оценки фильтра.

## 4. Алгоритм `SnsGuard`

### 4.1. Интерфейс

```cpp
bool SnsGuard::update(const SnsSample &s, double imu_time, const ins::KalmanConfig &cfg);
```

- `s` — текущий кадр СНС (время `s.time`, координаты, скорости, углы).
- `imu_time` — текущее время счисления по ИМУ (используется для детекта STALE при отсутствии новых кадров).
- `cfg` — конфигурация (`ins::kalman_cfg`).
- Возвращает `true`, если кадр разрешён для коррекции.

### 4.2. Логика `update`

1. **Новый кадр?** `is_new_frame = !has_seen || s.time != last_seen_time`.
2. **Если новый кадр:** обновить `first_seen_time/last_seen_time/has_seen`, вызвать `validate(s, cfg)`.
3. **Если кадр не новый (тот же `s.time`):** повторную валидацию не выполнять. Проверить таймаут пропадания:
   - `t_ref = has_accepted ? last_accepted.time : first_seen_time`
   - если `imu_time - t_ref > cfg.gnss_silence_timeout_s` → `status = STALE`
4. **Решение:** `return (cfg.gnss_guard_on <= 0.5) || (status == SnsStatus::VALID)`.

При выключенной защите (`gnss_guard_on <= 0.5`) любые кадры допускаются — это обеспечивает обратную совместимость/возможность отключения.

### 4.3. Валидация нового кадра (уровень 1)

Проверки выполняются последовательно; при первой ошибке кадр помечается `INVALID` с причиной `reject`, инкрементируется `rejected_frames`.

| № | Проверка | Условие отбраковки | `SnsReject` |
|---|---|---|---|
| 1 | Конечность значений | Любое из `lat,lon,alt,vn,vh,ve,heading,roll,pitch,time` не `isfinite` | `NONFINITE` |
| 2 | Диапазоны координат | `|lat| > 90°` или `|lon| > 180°` (в радианах) | `RANGE` |
| 3 | Zero-fix | `|lat| < 1e-7` и `|lon| < 1e-7` | `ZERO_FIX` |
| 4 | Правдоподобие скорости | `max(|vn|,|vh|,|ve|) > gnss_vel_plaus` | `SPEED` |
| 5 | Полоса по высоте | Первый принятый кадр задаёт `alt0`; далее `|alt - alt0| > gnss_alt_band_m` | `ALTITUDE` |
| 6 | Корректность времени | При наличии `last_accepted`: `dt = s.time - last_accepted.time`; отбраковка если `dt <= 0` или `dt > gnss_dt_max_s` | `TIME` |
| 7 | Скачок позиции (3D) | `dpos_h = R_E * sqrt(dlat^2 + (dlon*cos(lat_mid))^2)`, `dpos3 = sqrt(dpos_h^2 + dalt^2)`; если `dpos3 > gnss_jump_pos_m` | `JUMP_POS` |
| 8 | Скачок скорости | `dvel = sqrt(dvn^2 + dvh^2 + dve^2)`; если `dvel > gnss_jump_vel_ms` | `JUMP_VEL` |

При успешном прохождении: `status = VALID`, `reject = NONE`, `last_accepted = s`, `has_accepted = true`, `accepted_frames++`.

### 4.4. Детект пропадания (уровень 2)

Пропадание фиксируется не по содержимому кадра, а по факту отсутствия **нового** кадра СНС относительно времени ИМУ:
- Если `SnsReader` продолжает отдавать кадр с тем же `s.time`, `validate` не вызывается повторно.
- Если `imu_time - t_ref > gnss_silence_timeout_s` (`t_ref` — время последнего принятого или первого увиденного кадра) — `status` становится `STALE`.
- В `STALE` коррекция по СНС блокируется, БИНС работает в режиме свободной инерции до появления нового `VALID` кадра.

## 5. Взаимодействие с блоками проекта

### 5.1. `data_io::SnsReader` / `data_io`
`SnsReader` формирует `nav::SnsSample` из `gps.dat`/`angle.dat` (или соответствующих CSV-источников в пайплайне проекта). `SnsGuard` **не меняет** логику чтения/парсинга — он потребляет уже готовый `SnsSample`. Это важно: защита не зависит от формата файла, только от значений полей.

### 5.2. `ins::ins_filter` (фильтр Калмана)
- `ins::correct(bins, ref.measurement(), st.x, st.P)` вызывается **только** при `sns_ok == true`.
- Вектор измерений `z` в терминах фильтра строится внутри `ins::correct` как невязка `(bins - sns)`. Защита предотвращает подачу аномального `sns` (`ref.measurement()`), тем самым предотвращает некорректное обновление `x`, `P`, `K`.
- При заблокированном кадре выполняется только `predict` (на каждом такте ИМУ) — ковариация растёт согласно `Q`, оценки эволюционируют по модели без внешней коррекции. Это штатное поведение ESKF/ИНС в режиме пропадания СНС.
- Параметры защиты вынесены в `ins::KalmanConfig` рядом с `kalman_cfg`, что позволяет настраивать их централизованно.

### 5.3. `nav::NavState` и обратная связь по ошибкам
При `VALID` кадре после `correct`:
- Компоненты `st.x[0..8]` (ошибки координат/скорости/углов) вычитаются из `st.lat/lon/alt/V/att`.
- Смещения `st.ba/st.bg` корректируются на `st.x[9..14]`.
- Вектор `st.x` обнуляется.

При `INVALID/STALE`:
- `correct` не вызывается, `NavState` не корректируется по СНС.
- `st.x` обнуляется, в лог пишется текущая оценка `hdg_true` и состояние. Это предотвращает накопление/повторное применение устаревших ошибок при пропуске коррекции.

### 5.4. `SnsSample::sig_scale` и VO/другие подсистемы
В данном проекте `SnsSample` содержит `sig_scale` (масштаб сигм измерений, резерв/используется VO). `SnsGuard` читает только стандартные поля (`time, lat, lon, alt, vn, vh, ve, heading, roll, pitch`) и не модифицирует `sig_scale`. Конфликтов с VO-пайплайном не создаёт.

### 5.5. Логирование
`SnsGuard` хранит счётчики `accepted_frames/rejected_frames`, последнюю причину `reject`, `status`, диагностические `last_dt/dpos/dvel`. В текущей интеграции в `main.cpp`/`trajectory.h` отдельный файл `gnss_guard.txt` **не пишется** (минимальная интеграция). При необходимости можно добавить вывод сводки в конце `main()` или отдельный логгер при необходимости.

## 6. Параметры по умолчанию

| Параметр | Значение по умолчанию | Примечание |
|---|---:|---|
| `gnss_guard_on` | `1.0` | Защита включена |
| `gnss_vel_plaus` | `500.0` м/с | Верхний предел правдоподобной скорости |
| `gnss_silence_timeout_s` | `5.0` с | Таймаут до `STALE` при отсутствии новых кадров |
| `gnss_alt_band_m` | `5000.0` м | Допуск по высоте от `alt0` первого принятого кадра |
| `gnss_dt_max_s` | `3600.0` с | Максимальный разрыв времени между принятыми кадрами |
| `gnss_jump_pos_m` | `1000.0` м | Порог 3D-скачка позиции |
| `gnss_jump_vel_ms` | `100.0` м/с | Порог скачка скорости |

Значения являются стартовыми (консервативными) и должны уточняться под конкретный сценарий/датасет (наземный/БПЛА, качество GNSS, частота кадров, динамика).

## 7. Ограничения и дальнейшие шаги

- **Стартовый участок (180 с)** в `main.cpp` использует отдельную логику и не проходит через `nav::step` с защитой. При необходимости защиту можно распространить и на него.
- **Порог `ALTITUDE`** привязан к `alt0` первого принятого кадра. Для полётов с большим набором высоты относительно старта порог `gnss_alt_band_m` нужно увеличить или заменить на относительный контроль.
- **Проверка `JUMP_POS/JUMP_VEL`** выполняется относительно `last_accepted` (последнего **принятого**). Это корректно для фильтрации выбросов, но при длительном `STALE` первый вернувшийся кадр сравнивается со старым принятым — пороги должны это учитывать.
- **Конфигурация** сейчас берётся из `ins::kalman_cfg` (дефолты в коде). Для воспроизводимости желательно добавить чтение параметров из INI/конфига проекта.
- **Диагностика.** Рекомендуется добавить запись `gnss_guard.txt`/сводки (accepted/rejected, причины, время STALE) для анализа на реальных данных.
- **Тестирование.** Необходимо прогнать на штатных данных проекта и на сценариях с артефактами СНС (нули, NaN, скачки, пропадания), сравнить траекторию/ошибки до и после включения защиты. При валидных данных поведение должно остаться близким к исходному.

## 8. Краткий итог

`SnsGuard` добавляет в `ITT_Students-VO-FastFreak-homography` слой допуска СНС-измерений перед `ins::correct`. Он работает в связке `SnsReader -> nav::step -> guard.update -> (VALID ? ins::correct+apply : inertial only)`, использует параметры `ins::KalmanConfig`, отслеживает валидность кадра и таймаут пропадания, и минимально вмешивается в существующую архитектуру ИНС/ESKF.
