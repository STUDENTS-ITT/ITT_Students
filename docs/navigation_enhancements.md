## 1. Матричная экспонента для F и Q (П8/П9)

### 1.1 Что сейчас

`Fj_matrix` (`src/ins/ins_filter.h:91`) строит первый порядок: `F = I + T·A`, все элементы `A` уже умножены на `T`. `Qj_matrix` (`src/ins/ins_filter.h:35`) — диагональ `σ²·T`. Такое приближение корректно только для очень малых `T`.

### 1.2 Точная дискретизация

Непрерывная модель ошибок `ẋ = A·x + G·w` с шумом `Q_c`. Точные формулы для шага `T`:

```
F_d = e^{A·T} = Σ_{k=0..∞} (A·T)^k / k!
Q_d = ∫₀^T e^{A·τ}·G·Q_c·Gᵀ·e^{Aᵀ·τ} dτ
```

Разложение `Q_d` по степеням `T` (удобно на имеющихся `multiply_matrix`/`matrix_sum`):

```
Q_d = T·Q_c⁰ + (T²/2!)·(A·Q_c⁰ + Q_c⁰·Aᵀ)
            + (T³/3!)·(A²·Q_c⁰ + A·Q_c⁰·Aᵀ + Q_c⁰·(Aᵀ)²) + ...
```

где `Q_c⁰ = G·Q_c·Gᵀ` — шум, внесённый в уравнения: `σ_a²` в строки скорости (3..5), `σ_g²` в строки углов (6..8), `σ_ba²`/`σ_bg²` в строки смещений (9..14). У координат (0..2) шума нет — он «перетекает» туда только через связи `A`, что и учитывает точная `Q_d`.

### 1.3 Насколько это существенно

При `T = 5 мс` (IMU_RATE_HZ = 200) и `f` до 30 м/с²: элемент `T·(−n×f) ≈ 0.15`, поправка второй степени `(A·T)²/2 ≈ 0.011` — **около 7%** к блоку «скорость←углы». На спокойном участке — единицы процентов. Для манёврового участка поправка заметная; но главный выигрыш — корректная недиагональная `Q_d`: шум акселя/гиро согласованно влияет на скорости и координаты, ковариация не занижается по «скрытым» перекрёстным каналам.

### 1.4 Реализация без внешних библиотек

**Путь 1 — ряд Тейлора:**

```cpp
// A — строится БЕЗ умножения на T (перенести это обратно из Fj_matrix)
const Matrix I = E_matrix(KF_STATE);
Matrix Fd = matrix_sum(I, multiply_scalar(A, T), KF_STATE);
const Matrix A2 = multiply_matrix(A, A, KF_STATE, KF_STATE);
Fd = matrix_sum(Fd, multiply_scalar(A2, T * T / 2.0), KF_STATE);
// при желании (T³/6)·A³ — на T=5 мс пренебрежимо мало
```

`Q_d` — по разложению из 1.2 (термы `A·Q_c⁰`, `Q_c⁰·Aᵀ`, при желании `A²·Q_c⁰`, `A·Q_c⁰·Aᵀ`, `Q_c⁰·(Aᵀ)²`); нужен `multiply_scalar` для `σ`-квадратов (либо уже имеющиеся операции).

**Путь 2 — метод Ван Лоуна (один вызов expm):**

```
Φ = expm( [[ A,  Q_c⁰ ], [ 0, −Aᵀ ]] · T )      // матрица 2·KF_STATE × 2·KF_STATE
```

тогда `Φ[0..n][0..n] = F_d`, `Φ[0..n][n..2n] = Q_d`. Нужна собственная `expm` по Тейлору (10–15 строк на `multiply_matrix`), но `F` и `Q` получаются одним вызовом и автоматически согласованы.

### 1.5 Архитектурное следствие

`Q_d` зависит от `A` (то есть от `C`, `f_nav`, `att`, `lat`), а `A` меняется каждый такт. Значит `Qj_matrix(T)` перестаёт быть константой — её нужно вычислять вместе с `F` в `predict` (`src/ins/ins_filter.h:164`). Рекомендация: ввести единую функцию-хелпер `discretize(A, Q_c⁰, T)` → `(Fd, Qd)` и вызывать её из `predict`.

Править:
- `src/ins/ins_filter.h` — `Fj_matrix`, `Qj_matrix`, `predict`; добавить `multiply_scalar`, `discretize`, `expm` (при Пути 2).

## 2. Адаптивное Q при манёвре

### 2.1 Проблема постоянного Q

Малая `Q` на манёвре → недооценка `P` → фильтр «схлопывается», перестаёт отслеживать измерения (инновации отсекаются гейтом). Большая `Q` на прямолинейном участке → избыточный шум, размытая оценка. Нужно масштабировать `Q` по фактической динамике.

### 2.2 Вариант A — детектор манёвра (детерминированно, по физике)

Сигнал уже вычисляется в `src/navigation/maneuver_tilt.h` (адаптация `R` по акселю, гейт). Расширить на `Q`:

```
man_score = max( |f_nav|/g − 1,  |ω_body|/ω_thr,  0 )
Q_man = Q · max(1, man_score²)
```

`predict` получает `double man_factor` (из `trajectory.h::step`, где уже есть `evalAccelAttitude` и гейт) и масштабирует диагональные блоки скорости (3..5) и углов (6..8):

```cpp
// в predict (или в discretize): 
// at(Q,3,3,KF_STATE)*=manf*manf; ...блоки 3..5 и 6..8
```

Плюс: просто, устойчиво, нет обратных связей. Минус: пороги подбираются.

### 2.3 Вариант B — ковариационное согласование по инновациям

Онлайн-оценка реальной статистики инноваций в окне `W` и коррекция `Q`:

```
Ŝ = (1/W)·Σ ν_k·ν_kᵀ          (эмпирическая ковариация инноваций)
S_теор = H·P·Hᵀ + R
α = diag(Ŝ) / diag(S_теор)
Q_vel/att ← Q_vel/att · α      (сглаживание EMA, обрезка α ∈ [0.5; 10])
```

Плюс: без порогов, самоподстраивается. Минус: риск при редких измерениях (малое `W`) и возможность резонанса со своим же масштабированием — обязательны: EMA-сглаживание, минимальный размер окна, обрезка `α`, применение только при достаточном числе инноваций.

### 2.4 Рекомендация

Начать с варианта A, переиспользуя существующий гейт в `maneuver_tilt.h`. Правки: `src/ins/ins_filter.h` — параметр `man_factor` в `predict` (и в `discretize`); `src/navigation/trajectory.h` — вычисление `man_factor` из имеющейся динамики.

## 3. Оценка временной рассинхронизации δt

### 3.1 Откуда берётся ошибка

СНС-приёмник выдаёт коррекцию с задержкой `δt` (десятки–сотни мс): измерение сделано в момент `t_meas = t_now − δt`, применяется к состоянию на `t_now`. При скорости `V` получаем смещение позиции `≈ V·δt`, при ускорении `a` — ошибку скорости `≈ a·δt`. Аналогично для VO.

### 3.2 Особенности данных

В `gps.dat`/`imu.dat` есть колонка `timestamp_ns`, но сейчас читается только `time_s` (`src/data_io/data_reader.cpp:163`). Общие `time_s` у СНС и ИМУ уже синхронизированы, но фактическая задержка приёмника в файле не отражена — её моделируют состоянием фильтра либо калибруют офлайн.

### 3.3 Вариант A — состояние δt в фильтре

Добавить состояние `δt` (например, `x[22]`, если задействованы l/f/s из `camera_state_extension.md`; без них — `x[15]` с переиндексацией):

```
F:   F[δt][δt] = 1          (случайное блуждание, малый Q ≈ (1e-3)²·T)
P0:  p_δt = (0.1)²           (неопределённость 0.1 с)
```

**Матрица наблюдения** для строк позиции (единицы согласованы с x[0..2]: широта/долгота в рад, высота в м):

```cpp
H[0][δt] =  Vn / R_EARTH;               // δφ  ← δt
H[1][δt] =  Ve / (R_EARTH·cosφ);        // δλ  ← δt
H[2][δt] =  Vh;                          // δh  ← δt
// строки скорости (опционально): производная по времени
H[3][δt] = a_n;  H[4][δt] = a_h;  H[5][δt] = a_e;   // ускорение в навигационной СК
```

Инновация `z = БИНС − СНС` частично объясняется `δt`. После коррекции — инжекция `st.sync += st.x[δt]` и `st.x[δt] = 0` (та же схема, что для `lc/fc/scale`).

**Наблюдаемость:** нужен `V ≠ 0` (или `a ≠ 0`). На стоянке δt не наблюдаем — малая `Q` не даст увести состояние. На участке с постоянной скоростью δt неотделим от постоянного смещения позиции; разделяются на разгоне/повороте.

### 3.4 Вариант B — офлайн-калибровка по записи

Перебор `δt ∈ [0; 0.2 с]` шагом 1 мс в Python (`tools/`): для каждого значения пересобрать инновации и выбрать то, что минимизирует сумму квадратов (или пик кросс-корреляции СНС-сигнала с БИНС-сигналом). Подходит, когда задержка стабильна в пределах записи.

### 3.5 Правки

- `src/ins/ins_filter.h` — расширение вектора состояния, блок `H` (+1 столбец), F/Q/P0 для δt.
- `src/navigation/trajectory.h` — инжекция и обнуление `st.sync`.
- `src/navigation/aligner.h` — `initialCovariance` (добавить `p_δt`).

## 4. Loop closure / factor graph (iSAM2)

### 4.1 Чем отличается от текущего ESKF

ESKF — разовый проход: вся история сжимается в `(x, P)`, вернуться к прошлым кадрам нельзя. Факторный граф хранит все ключевые кадры и позволяет добавить связь «текущий кадр ↔ старый кадр» (петля) и переоптимизировать траекторию. Решает главную слабость ESKF — накопленный дрейф при потере СНС: петли его ограничивают; даже при наличии СНС граф даёт более гладкий трек.

### 4.2 Структура графа для БИНС + СНС + VO

Вершины — позы аппарата в ключевые моменты (position + attitude; по желанию velocity/bias):

- **IMU factor** между соседними ключевыми кадрами — вместо счисления (preintegration: относительное измерение приращения позы по ИМУ за интервал);
- **GPS factor** — абсолютные позиция/скорость на ключевых кадрах (те же 9 компонент, что в ESKF);
- **VO factor** — относительная поза между кадрами (плечо/установка — из `camera_state_extension.md`);
- **Loop closure factor** — относительная поза между текущим и переоткрытым кадром.

Замыкание петель: детектор узнавания сцены (признаковое сравнение, DBoW/VLAD) → найденная пара кадров добавляет связь; решение — нелинейные наименьшие квадраты на группе `SE(3)` (Gauss-Newton / Levenberg–Marquardt в log-map).

### 4.3 iSAM2 vs батч

iSAM2 (GTSAM) решает граф инкрементально через Bayes tree — только локальные части графа — подходит для онлайн. Репозиторий придерживается политики «без внешних библиотек», поэтому:

- **Офлайн/post-обработка** (минимум усилий): записывать ключевые кадры (поза + время + ковариация) и факторы (IMU/GPS/VO/loop) в лог; `tools/` Python-скрипт (numpy разрешён) оптимизирует граф маленьким собственным LM-солвером над позами; результат сравнивается с `result.txt`.
- **Полноценно в C++**: компактный факторный граф (поза-граф) с собственным LM — умеренный объём (~200–400 строк), но заметная переделка. Подключение GTSAM требует пересмотра политики зависимостей.

### 4.4 Промежуточный план

1. В `trajectory.h::step` — периодическая запись ключевых кадров (`keyframe.dat`: time, pose, P-квадратичные корни).
2. Сначала только офлайн-поза-граф на Python с GPS+VO факторами — проверить выигрыш на имеющихся записях.
3. Добавить детектор петель и сравнить сжатие дрейфа при выключенной СНС на участках.
4. Если результат оправдан — перенести LM в C++.
