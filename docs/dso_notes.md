# Алгоритм видеонавигации DSO

**DSO** (Direct Sparse Odometry) — прямая разреженная монокулярная одометрия, предложенная Jakob Engel, Vladlen Koltun и Daniel Cremers (TUM, 2016–2018). В отличие от VINS-Mono, использует **только камеру**: ни IMU, ни другого датчика в схеме нет.

Оригинальная статья: [Engel, Koltun, Cremers. *Direct Sparse Odometry*](https://arxiv.org/abs/1607.02565).
Код: [JakobEngel/dso](https://github.com/JakobEngel/dso).

---

## 1. Прямой метод против метода по признакам

Это главная развилка, определяющая всё остальное.

**Непрямые методы** (ORB-SLAM, VINS-Mono) работают в два шага: сначала детектор находит углы и вычисляет дескрипторы, затем оптимизация минимизирует **геометрическую** невязку — расстояние в пикселях между спроецированной точкой и её наблюдением. Изображение при этом используется лишь как источник координат точек: после детекции сами яркости выбрасываются.

**Прямые методы** (LSD-SLAM, DSO) пропускают шаг детекции и минимизируют **фотометрическую** невязку — разность яркостей пикселей напрямую:

\[
E_{\mathbf{p}j} = \sum_{\mathbf{p}\in\mathcal{N}_\mathbf{p}} w_\mathbf{p}
\left\|
(I_j[\mathbf{p}'] - b_j) - \frac{t_j e^{a_j}}{t_i e^{a_i}} (I_i[\mathbf{p}] - b_i)
\right\|_\gamma .
\]

Здесь \(I_i, I_j\) — яркости в опорном и целевом кадрах, \(t\) — время экспозиции, \((a, b)\) — аффинные параметры яркости, \(\|\cdot\|_\gamma\) — норма Хьюбера.

Что из этого следует практически:

- **Плюс.** Можно использовать любые пиксели с ненулевым градиентом, а не только углы. На слабо текстурированной сцене — гладкая стена, ровное поле — где детектор углов почти ничего не находит, DSO работает по краям и слабым перепадам яркости.
- **Плюс.** Нет расхода на детекцию и дескрипторы, нет ошибок сопоставления как отдельного источника выбросов.
- **Минус, определяющий.** Требуется **постоянство яркости**. Автоматическая экспозиция, изменение освещённости, отражения нарушают это предположение напрямую. Отсюда — необходимость фотометрической калибровки.
- **Минус.** Малый радиус сходимости. Прямая оптимизация работает по градиенту яркости и требует хорошего начального приближения; при большом смещении между кадрами она уходит в локальный минимум. Дескрипторы у непрямых методов такого ограничения не имеют.

## 2. Фотометрическая модель камеры

Ключевой вклад DSO по сравнению с предшественниками — не просто использование яркостей, а их **корректная физическая модель**. Наблюдаемая яркость связана с облучённостью так:

\[
I(\mathbf{x}) = G\bigl(t\, V(\mathbf{x})\, B(\mathbf{x})\bigr),
\]

где \(B\) — облучённость, \(V\) — виньетирование (падение яркости к краям кадра), \(t\) — время экспозиции, \(G\) — нелинейная функция отклика сенсора.

Зная \(G\) и \(V\), можно восстановить фотометрически корректное изображение:

\[
I'(\mathbf{x}) = t\,B(\mathbf{x}) = \frac{G^{-1}\bigl(I(\mathbf{x})\bigr)}{V(\mathbf{x})} .
\]

Калибровка выполняется отдельным инструментом и даёт два файла: `pcalib.txt` (обратная функция отклика) и `vignette.png` (карта виньетирования).

**Если калибровки нет** — а её нет ни для EuRoC, ни для съёмки бытовым дроном — DSO запускают с `mode=1`. Тогда \(G\) и \(V\) считаются тождественными, а компенсация возлагается только на аффинные параметры \((a_j, b_j)\), оцениваемые для каждого кадра в общей оптимизации. Это существенно слабее: аффинная модель — глобальная поправка на весь кадр, а виньетирование пространственно неоднородно.

Именно поэтому DSO чувствительнее к автоэкспозиции, чем VINS-Mono, и на реальном дроновом видео эта разница заметна.

## 3. Выбор точек

DSO не ищет углы, но и не берёт все пиксели подряд: сохраняется около **2000** точек-кандидатов на кейфрейм.

Отбор устроен так:

1. Кадр делится на блоки 32×32.
2. В каждом блоке порог градиента адаптивный: медиана градиента по блоку плюс константа. Это обеспечивает точки и в контрастных, и в блёклых областях.
3. Отбор идёт в три прохода со всё большими блоками и понижающимся порогом, чтобы покрытие получилось **равномерным по кадру**.
4. Итоговое число подстраивается регулятором под целевое значение.

Равномерность важна: концентрация точек в одном углу изображения делает задачу плохо обусловленной по вращению.

Каждая точка представлена **шаблоном из 8 пикселей** в форме, разнесённой по направлениям — компромисс между устойчивостью (больше пикселей — меньше шум) и вычислительной стоимостью.

## 4. Структура окна оптимизации

DSO поддерживает окно из **7 активных кейфреймов** и совместно оптимизирует:

- позы всех кейфреймов окна;
- **обратные глубины** всех активных точек;
- внутренние параметры камеры \(f_x, f_y, c_x, c_y\) (да, DSO уточняет калибровку на ходу);
- аффинные параметры яркости \((a, b)\) для каждого кадра.

Оптимизация — гауссова-ньютоновская, с маргинализацией через дополнение Шура и с **фиксацией точки линеаризации** (First Estimate Jacobians), чтобы маргинализация не вносила ложную информацию.

### Кандидаты и активация

Точка не попадает в оптимизацию сразу. Сначала она — **кандидат** (immature point) с широким интервалом глубины. По мере поступления новых кадров интервал сужается поиском вдоль эпиполярной линии. Когда неопределённость становится достаточно малой, точка **активируется** и включается в общую оптимизацию. Такая двухстадийность экономит вычисления и отсекает ненадёжные точки до того, как они испортят решение.

### Стратегия кейфреймов

Три критерия создания нового кейфрейма:

- изменение поля оптического потока (движение);
- поток без учёта вращения (то есть чистая трансляция — важно, ведь только она даёт параллакс);
- изменение экспозиции.

Маргинализация: удаляются кейфреймы, у которых мало общих точек с последним, а также поддерживается разрежённое покрытие пространства.

## 5. Чего в DSO нет

Перечень «отсутствующего» здесь так же важен, как перечень возможностей, — именно он определяет пригодность для навигации.

| Отсутствует | Последствие |
|---|---|
| **IMU** | нет метрического масштаба, нет наблюдаемого направления вертикали |
| **Замыкание петель** | дрейф не компенсируется при возврате в известное место |
| **Распознавание места** | нет восстановления после потери трекинга |
| **Глобальная оптимизация** | согласованность только в пределах окна |
| **Дескрипторы** | нет сопоставления между удалёнными по времени кадрами |

DSO — это **чистая одометрия**, не SLAM. Он последовательно оценивает движение и не строит согласованную глобальную карту.

Дрейф DSO имеет **7 степеней свободы** — полная группа Sim(3): три вращения, три сдвига и масштаб. Для сравнения, у VINS-Mono дрейф всего в 4 степенях свободы, потому что IMU фиксирует вертикаль и масштаб.

## 6. Проблема масштаба и что она значит для ИНС

Монокулярная камера принципиально не различает «маленький объект близко» и «большой далеко». Формально: для любой траектории \(\{\mathbf{T}_i\}\) и структуры \(\{\mathbf{X}_j\}\) масштабированный вариант \(\{s\mathbf{T}_i\}, \{s\mathbf{X}_j\}\) даёт **точно те же** изображения. Наблюдения не содержат информации, позволяющей выбрать \(s\).

VINS-Mono решает это через IMU: акселерометр измеряет ускорение в м/с², и двойное интегрирование даёт метрику. Ценой того, что масштаб наблюдаем лишь при достаточном ускорении.

DSO не решает это никак. Его выход — траектория в условных единицах.

Для подачи в слабосвязанную ИНС масштаб обязателен, и брать его приходится извне:

1. **Высота над точкой взлёта** — барометр или радиовысотомер. В MARS-LVIG есть топик `height_above_takeoff`.
2. **Начальный участок GPS** — оценка \(s\) методом Умеямы, пока приём есть, затем автономный полёт с фиксированным \(s\).
3. **Известная высота над землёй при надирной съёмке** — для отвесной съёмки над плоскостью масштаб прямо связан с высотой полёта, и это самый естественный источник в нашей задаче.

Дополнительная тонкость: масштаб не только неизвестен, но и **дрейфует**. Оценив его один раз в начале, вы получите постепенно нарастающую систематическую ошибку в пройденном пути. Это отдельная составляющая погрешности, которую надо измерить и указать.

## 7. Формат входных данных

DSO читает папку с изображениями (или zip-архив) плюс текстовые файлы:

```
последовательность/
├── images/        кадры, сортируются по имени
├── times.txt      "id  метка_времени  экспозиция"
├── camera.txt     калибровка
├── pcalib.txt     функция отклика     (необязательно)
└── vignette.png   виньетирование      (необязательно)
```

Тонкость, на которой легко споткнуться: `times.txt` DSO ищет в **родительском** каталоге папки с кадрами. При `files=<...>/seq/images` файл должен лежать по пути `<...>/seq/times.txt`.

Формат `camera.txt`:

```
RadTan fx fy cx cy k1 k2 p1 p2
in_width in_height
crop
out_width out_height
```

Поддерживаются модели `Pinhole`, `RadTan`, `EquiDistant`, `FOV`. Выходной размер желательно кратен 8.

### Основные ключи запуска

| Ключ | Смысл |
|---|---|
| `preset=0` | точность, все кадры, без ограничения по времени |
| `preset=1` | быстрый режим |
| `preset=2/3` | 5×-ускоренные варианты, меньше точек |
| `mode=0` | есть фотометрическая калибровка |
| `mode=1` | **калибровки нет** — наш случай |
| `mode=2` | нет калибровки и нет данных об экспозиции |
| `playbackSpeed=0` | последовательная обработка, кадры не пропускаются |
| `playbackSpeed=1` | реальное время, лишние кадры отбрасываются |
| `nogui=1` | без визуализации — обязательно при замерах времени |
| `quiet=1` | без подробного вывода |

Выход — `result.txt` в формате TUM: `timestamp tx ty tz qx qy qz qw`, **в условном масштабе**.

## 8. Особенности, влияющие на надирную аэросъёмку

**Плоская сцена.** Как и у VINS-Mono, инициализация страдает: DSO стартует, задавая всем точкам одинаковую начальную глубину и уточняя её по мере движения. Над идеально ровной поверхностью этот процесс сходится, но плохо обусловлен — глубина и масштаб смешиваются.

**Большая высота.** Малый параллакс относительно глубины означает слабую наблюдаемость обратной глубины. Прямые методы к этому чувствительны сильнее непрямых, потому что фотометрическая невязка вдоль эпиполярной линии на однородной текстуре очень пологая.

**Однородная текстура.** Здесь у DSO преимущество: он берёт точки с любым градиентом, а не только углы, поэтому на поле, где детектор Харриса почти ничего не найдёт, DSO точки получит.

**Автоэкспозиция.** Главный риск, разобран в разделе 2.

**Сжатие видео.** Если кадры получены из mp4, межкадровое сжатие вносит артефакты именно в яркости. Прямой метод страдает от этого больше, чем признаковый.

## 9. Сводка алгоритма

```
для каждого нового кадра:
    трекинг: прямое выравнивание изображения относительно опорного
             кейфрейма по фотометрической невязке (пирамида, грубо-точно)
    если трекинг сорван -> LOST (восстановления нет)

    решить, кейфрейм ли кадр (оптический поток, поток без вращения, экспозиция)

    если НЕ кейфрейм:
        уточнить интервалы глубины точек-кандидатов вдоль эпиполярных линий

    если кейфрейм:
        активировать созревшие кандидаты
        отобрать новые кандидаты (~2000, равномерно по кадру)
        оптимизировать окно: 7 кейфреймов, глубины, интринсики, (a,b)
        маргинализировать старые кейфреймы и точки (дополнение Шура, FEJ)
```

## 10. Сравнение с VINS-Mono в одной таблице

| Признак | VINS-Mono | DSO |
|---|---|---|
| Что минимизируется | репроекционная невязка | фотометрическая невязка |
| Датчики | камера + IMU | только камера |
| Метрический масштаб | есть | **нет** |
| Вертикаль наблюдаема | да, по гравитации | нет |
| Степеней свободы дрейфа | 4 | 7 |
| Замыкание петель | есть (DBoW2 + граф 4-DoF) | нет |
| Восстановление после сбоя | есть | нет |
| Оптимизация | Ceres, скользящее окно | своя гауссова-ньютоновская, окно 7 кадров |
| Число точек в окне | ~150 признаков | ~2000 точек |
| Уточнение интринсиков | нет | **да** |
| Фотометрическая калибровка | не нужна | желательна |
| Калибровка камера–IMU | критична | не нужна |
| Устойчивость к автоэкспозиции | высокая | **низкая** |
| Работа на слабой текстуре | хуже | **лучше** |
| Прямое подключение к слабосвязанной ИНС | да | нет |
