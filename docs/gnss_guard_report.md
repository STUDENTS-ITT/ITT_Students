## 2. Что реализовано

### 2.1 Уровень 0 — устойчивый разбор строк

**Файл:** `src/core/data_io/data_reader.cpp`.

Исходная проблема: `std::stod` бросает исключение на нечисловом поле, обработчика нет — одна испорченная строка `gps.dat` роняла весь прогон.

Внесено: функции разбора обёрнуты в `try`/`catch`, при неудаче строка пропускается, чтение продолжается со следующей:

| Функция | Строка | Обработка |
|---|---|---|
| `parseTimestamp` | `data_reader.cpp:89` | `try`/`catch` (`:99–104`) |
| разбор строки IMU | `:268–281` | `try`/`catch`, пропуск через `continue` |
| `parseGpsLine` | `:171` | `try`/`catch` (`:189–199`, `:210–221`) |
| цикл чтения GPS | `:377–379` | `if (!parseGpsLine(...)) continue;` |

**Отклонение от черновика (раздел 5.1):** испорченная строка пропускается **молча** — она не помечается `INVALID` и не попадает в счётчики. Причина: `SnsStatus` описывает только отсчёты, дошедшие до `nav::step()`, а строки, отброшенные на разборе, в него не попадают. Практическое следствие — в логе `gnss_guard.txt` не видно числа отброшенных при разборе строк (см. раздел 4.2).

### 2.2 Уровень 1 — самодостаточная валидация

**Файл:** `src/core/navigation/gnss_guard.h`, метод `SnsGuard::validate()` (`:129`).

Порядок проверок в коде и соответствующие коды отказа (`nav::SnsReject`):

| № | Проверка | Код отказа | Порог |
|---|---|---|---|
| 1 | конечность девяти компонент измерения и времени | `NONFINITE` | `std::isfinite` |
| 2 | диапазоны координат | `RANGE` | `\|lat\| ≤ 90°`, `\|lon\| ≤ 180°` |
| 3 | нулевой фикс | `ZERO_FIX` | `\|lat\|`, \|lon\| < `1e-7` рад |
| 4 | предельная скорость | `SPEED` | `maxSpeed() > gnss_vel_plaus` |
| 5 | полоса высоты | `ALTITUDE` | `±5000 м` от первого фикса |
| 6 | монотонность времени | `TIME` | `0 < Δt ≤ 3600 с` |
| 7 | кинематическое правдоподобие | `KINEMATICS` | `Δs ≤ v_plaus·Δt + acc_bound` |

Проверки 6–7 относятся к **последнему принятому** (`VALID`) фиксу, а не последнему прочитанному — иначе отказ становится опорой для следующей проверки. Опора обновляется только на принятых кадрах и не зависит от состояния гейта.

Константы-предохранители вынесены в `gnss_guard.h:38–40`: `SNS_ALT_BAND_M = 5000`, `SNS_ZERO_FIX_EPS_RAD = 1e-7`, `SNS_DT_MAX_S = 3600`. Они не являются «настройками подбора»: выход за них означает отказ датчика.

Особенность, согласованная с дизайном (раздел 5.2): после длительного перерыва опора устаревает, `Δt` в допуске формулы 7 растёт вместе с ним, и проверка **автоматически ослабевает** до приемлемой скорости полёта — возврат СНС после паузы не отсекается.

### 2.3 Уровень 2 — детектор молчания

**Файл:** `gnss_guard.h`, метод `SnsGuard::update()` (`:91`), ветка `:108–113`.

Отсчёт молчания идёт **по времени ИМУ**, а не по числу кадров СНС:

```
imu_time − t_ref > gnss_silence_timeout_s  →  STALE
```

где `t_ref` — время последнего принятого фикса, а до первого принятого — первый увиденный кадр. Поэтому отсутствие строк в `gps.dat` и обрыв связи с приёмником дают одинаковую реакцию: свободное счисление, рост `P`, состояние фильтра не трогается.

При этом разбор и валидация в `STALE` продолжаются (наблюдение не прерывается), что позволяет отличить «приёмник не отвечает» от «приёмник отвечает мусором» и обнаружить возврат СНС по факту прихода корректного отсчёта.

### 2.4 Точки интеграции

Логика размещена в `nav::step()` — месте, где есть номинал БИНС и `st.P`.

| Место | Что делает |
|---|---|
| `trajectory.h:54` | `SnsGuard sns_guard;` — член `NavState`, переживает такты |
| `trajectory.h:326` | `sns_ok = st.sns_guard.update(ref, time_s, ins::kalman_cfg)` — вызов на каждом такте ИМУ |
| `trajectory.h:327` | `manual = st.sns_guard.is_new_frame && !do_correction` — признак ручного отключения |
| `trajectory.h:328` | `apply_correction = do_correction && sns_ok` — итоговое разрешение |
| `simulation.cpp:393` | `do_correction = !in_outage && (hold_ref.time != prev_gps_time)` — ручное окно `outage_*` |
| `trajectory.h:376–388` | заполнение `SnsGuardRecord` и `sink.writeGuard(...)` |

Итоговое разрешение — конъюнкция трёх независимых источников (черновик, раздел 4.Г):

```
apply = ручное окно outage_* ∧ статус отсчёта = VALID ∧ разрешение гейта
```

При выключенной защите (`gnss_guard_on ≤ 0.5`) разрешение прежнее — поведение не меняется, но **наблюдение продолжается**, статус и причина фиксируются (`gnss_guard.h:117`). Это позволяет сравнивать прогоны «с защитой» и «без неё» на одном датасете.

### 2.6 Наблюдаемость

**Файл:** `src/core/data_io/data_writer.cpp:174` (`NavLogger::writeGuard`), файл `gnss_guard.txt` рядом с `result.txt`.

Запись ведётся **на каждом такте**, а не только при отказе, — иначе по логу невозможно восстановить хронологию перерыва. В строку попадают:

- `status` (`VALID` / `INVALID` / `STALE`) — свойство **отсчёта**;
- причина отказа (`SnsReject`) и метрики кадра `dt`, `dpos`, `dvel`;
- признак `new_frame`;
- флаг `manual` — активно ли ручное окно `outage_*`;
- накопительные счётчики `accepted` / `rejected`.

Раздельная запись `status`, причины и `manual` — обязательное условие разбора: по одной колонке нельзя установить, был ли отказ приёмника, сработала ли защита или коррекция отключена оператором. Итоговая сводка считается логгером по строкам (`SnsGuardRecord`), вторая копия счётчиков в `SnsGuard` не нужна.

### 3.2 Чистые данные — защита не меняет выдачу

На имеющихся наборах защита **не отклоняет ни одного кадра**, поэтому `result.txt` совпадает с прогоном без неё. Это выполняет критерий приёмки из черновика (раздел 9): на чистых данных защита не меняет траекторию в пределах численной погрешности.

Следствие: повторный подбор σ (этап 6 плана) пока не требуется — фактически применённых коррекций не изменилось. Он станет обязательным после внедрения уровней 3–6 (раздел 5), которые начнут реально отклонять кадры.

### 3.3 Инъекция дефектов

Прогон на наборе с внесёнными дефектами в копию `gps.dat` (`run_hk/data/raw`, обновление СНС 5 Гц): нулевой фикс, `nan`, телепорт, повтор времени.

Сводка `gnss_guard.txt` насчитала **три причины из четырёх**:

| Признак | Ожидалось | Получено |
|---|---|---|
| нулевой фикс | `zero_fix 1` | `1` |
| `nan` | `nonfinite 1` | `1` |
| телепорт | `kinematics 1` | `1` |
| повтор времени | `time 1` | **`0`** |

Четвёртый случай не сработал по известной причине (раздел 4.1). Контрольный опыт: замена повтора на время на 1 с назад дала ожидаемое `time 1` со значением `dt = −1.770850` в строке лога, то есть механизм `TIME` работает и фиксируется, — не срабатывает именно сценарий «то же время».

## 4. Известные ограничения реализации

### 4.1 Повтор времени не наблюдается

Кадр считается новым по изменению времени (`gnss_guard.h:93`):

```
is_new_frame = !has_seen || s.time != last_seen_time;
```

Строка с тем же временем, но другим содержимым, **не валидируется**: она не получает статус, причина не фиксируется, счётчики не растут. В логе такой такт выглядит как штатное удержание (`new = 0`) и неотличим от промежутка между фиксами. Проверка 7 (`Δt = 0`) доходит до кода только для выхода времени назад и слишком большого интервала (`gnss_guard.h:195`).

- **По результатам дефекта нет:** повторённый кадр по построению не может применить коррекцию (`do_correction = false` при `hold_ref.time == prev_gps_time`), телепорт через него не проходит, состояние фильтра не меняется.
- **Потеря в диагностике есть:** серия повторов не двигает опору молчания, поэтому через `gnss_silence_timeout_s` защита переходит в `STALE` и лог сообщает «СНС молчит», хотя приёмник отвечает данными.

Полный разбор и три варианта закрытия — `docs/gnss_guard_design.md`, разделы 14.2–14.3.

### 4.2 Отброшенные при разборе строки не считаются

Уровень 0 пропускает испорченную строку молча (раздел 2.1), поэтому число отброшенных при разборе строк в сводке отсутствует, хотя раздел 8 черновика его требует. `SnsGuardRecord` описывает только отсчёты, дошедшие до `nav::step()`.

### 4.3 Колонка `gate` — заглушка

Уровней 3–6 нет, поэтому состояние гейта в логе всегда `ENABLED`. Разделы черновика, опирающиеся на `SUSPECT` / `REJECTED` / `REACQUIRE` (доля времени в блокировке, число возвратов), сейчас неприменимы как метрики.

## 5. Будущие разработки

Нереализованные уровни 3–6 черновика (`docs/gnss_guard_design.md`, разделы 5.4–5.7) — план дальнейшей работы. Дополнительная задача — закрытие ограничений раздела 4.

### 5.1 Уровень 3 — гейт по инновации с состояниями

Единственный уровень, порог которого зависит от неопределённости. Расчёт в той же метрике, что и в `ins::correct()`:

```
S_pos = P[0..2, 0..2] + diag(σ_pos², σ_pos², σ_h²)
NIS   = z_posᵀ · S_pos⁻¹ · z_pos
```

срабатывание при `NIS > χ²₃(0.999) = 16.27`; практическая форма `thresh_pos = max(gnss_pos_floor_m, k·σ_pos_pred)`. **Нижний предел `gnss_pos_floor_m` обязателен**: типичный ESKF склонен к излишней уверенности, и чисто статистический критерий при заниженном `P` даёт ложные срабатывания.

Вводит состояния гейта `ENABLED → SUSPECT → REJECTED → REACQUIRE` и делает колонку `gate` в логе содержательной (закрывает ограничение 4.3).

**Зависимости:** `gnss_pos_floor_m`, `k`, `gnss_reject_streak`; расширение лога состояниями.

### 5.2 Уровень 4 — детектор скачка

Разовый выброс отличается от устойчивого расхождения второй разностью:

```
|dpos(t) − dpos(t−1)| > gnss_jump_step_m  →  мгновенный отказ кадра
```

Реакция за один кадр (вместо ожидания серии), состояние гейта и счётчик не расходуются. Закрывает требование «разовый скачок» из таблицы отказов (раздел 1 черновика).

**Зависимости:** `gnss_jump_step_m`, хранение предыдущей разности.

### 5.3 Уровень 5 — конечная блокировка с backoff

```
hold(n) = min(gnss_hold_s · 2^(n−1), gnss_hold_max_s)
```

Выход из `REJECTED` — двумя независимыми каналами: **по факту валидного отсчёта** (основной, быстрый) и **по таймеру** `t_reopen` (страховка, гарантия конечности). Счётчик `n` растёт только по факту неудачной пробы, молчание его не наращивает.

**Зависимости:** `gnss_hold_s`, `gnss_hold_max_s`, `gnss_stable_s`; состояния `SUSPECT`/`REJECTED`.

### 5.4 Уровень 6 — мягкое пересопряжение

Первый отсчёт после `REJECTED`/`STALE` обрабатывается в `REACQUIRE`: либо `R` раздувается пропорционально расхождению, либо шаг позиционной поправки ограничивается `gnss_step_max_m` за кадр. Возврат в `ENABLED` подтверждается серией успешных коррекций (`gnss_reacquire_s`), а не одним кадром.

Технически — необязательный скаляр в существующей `ins::correct()`: сигнатуры не меняются, ядро не трогается.

**Зависимости:** `gnss_step_max_m`, `gnss_reacquire_s`, `gnss_realign_m`; правка `ins::correct()`.

| Задача | Основание |
